# AGENTS.md — agent guide for `docgen-validate`

## Temporary local tool development

Prefer local symlinks to sibling tool checkouts when developing or testing
unreleased Voxgig tools together. Link to the actual package root (for example,
`apidef/ts` or `sdkgen/ts`), build that checkout, and verify that the consumer
resolves the linked code. Use existing validator local-path options where
available: this repo has `--docgen-path` and `--create-sdkgen-path`.

Do not create or copy `.zip`, `.tgz`, or `npm pack` snapshots into SDK projects
or ad hoc `vendor/` folders just to use local changes. Keep temporary links in
ignored dependency directories; keep machine-specific paths and temporary
`file:` dependencies out of committed manifests and lockfiles. Shared builds
and CI should use published versions or explicitly check out and build the
required source revisions.

## What this repo is

A harness that generates documentation for five real SDKs and checks it. It
tests `@voxgig/docgen`, not the SDKs. `sdkgen-validate` is the template it was
built from and the two are deliberately parallel; the spec lists do not
overlap, so between them they cover nineteen different APIs.

Read [`README.md`](./README.md) first: it carries the SDK table, the phase
list, and what `check-docs` asserts.

## The one rule that matters most

**A check that cannot fail is not a check.** Every assertion in
`bin/check-docs` has a matching case in `test/check-docs.test.cjs` that breaks
exactly one thing and requires that assertion to go red. When you add a check,
add its negative case in the same change. `make test` runs them.

This is not ceremony. The first cut of the manifest check passed against a
manifest with entries pointing at files that did not exist, because it only
counted entries.

## Why `check-docs` exists at all

`voxgig-docgen qa` reads `.sdk/doc/qa-manifest.json` and checks the prose,
local links and anchors of the files it lists. The manifest is generated by the
same run that generates the documentation, so qa cannot notice that an entity
is missing: the page is absent, the manifest does not list it, and every listed
page is clean.

`check-docs` reads the compiled model (`.sdk/model/sdk.json`) instead and asks
whether the documentation covers it. The two gates are complementary and
neither subsumes the other.

## Conventions

- Phases record `<name>_<phase>_rc=<n>` into `<run-dir>/summary.log`. The
  summarizer parses only that; do not make it read the phase logs.
- A non-zero rc for a phase after the first failure is not recorded, because
  the driver moves to the next SDK. Absent means "not reached", not "passed".
- Spec list format is `<name>:<repo>:<spec-file>`, resolved against the repo's
  own `.sdk/def/`. The SDKs are the source of truth for their specs; this repo
  does not vendor copies that can drift.

## Source code comments

Follow [COMMENT-POLICY.md](COMMENT-POLICY.md): comments are sparse and terse,
only for intricate or surprising code. Names carry intent; documents carry
requirements. Run `make comments comments-test` after editing source.
